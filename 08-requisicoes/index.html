01 · O CICLO

Como nasce uma requisição HTTP?

  1. Uma intenção vira um evento. Digitar uma URL, abrir um link, carregar uma imagem ou enviar um formulário pode iniciar uma requisição. Aqui, submit aciona o código.
  2. O navegador prepara o destino. Analisa a URL, verifica políticas e caches e, se necessário, resolve DNS e estabelece uma conexão. Uma conexão existente pode ser reutilizada.
  3. A mensagem sai. Método, destino, cabeçalhos e, quando aplicável, corpo são enviados segundo a versão HTTP negociada.
  4. O servidor responde. A borda ou aplicação processa a operação e retorna status, cabeçalhos e, quando aplicável, um corpo.
  5. A interface reage. A aplicação lê o JSON e atualiza o DOM ou apresenta um erro. Uma resposta HTTP de erro ainda é uma resposta recebida.
Nesta aplicação são duas etapas.

Nome da localidade → API de geocodificação → escolha de latitude/longitude → API de previsão → dados meteorológicos. A API de previsão recebe coordenadas, não o nome diretamente.

02 · CONTRATO HTTP

Métodos HTTP, frequentemente chamados de “verbos REST”

REST é um estilo arquitetural; usar GET e POST não torna uma API automaticamente REST. Métodos expressam a intenção da operação e existem independentemente desse estilo.

Safe significa sem alteração de estado solicitada; idempotente significa mesmo efeito pretendido ao repetir.
MétodoUso comumSafe?Idempotente?
GETConsultar um recursoSimSim
HEADConsultar metadados sem corpo de respostaSimSim
POSTSubmeter dados para processamento; pode criar um recursoNãoNão garantido
PUTCriar ou substituir o estado do recurso no URI escolhidoNãoSim
PATCHAplicar alterações parciaisNãoNão garantido
DELETESolicitar a remoção do recursoNãoSim
OPTIONSConsultar opções de comunicação; usado em preflight CORSSimSim

Logs e métricas podem mudar mesmo em métodos safe. DELETE repetido pode devolver outro status e continuar idempotente. PATCH pode ser projetado de forma idempotente. Esta aplicação envia somente GET às APIs públicas.

Endereços reservados para documentação, não medidos na sua consulta.
IP e TCP
IP transporta pacotes entre redes. TCP fornece um fluxo de bytes confiável e ordenado entre endpoints, com controle de conexão e retransmissão.
HTTP e HTTPS
HTTP define a comunicação de aplicação. HTTPS usa proteção TLS para confidencialidade, integridade e autenticação do servidor; não valida a qualidade ou a honestidade do conteúdo.
HTTP/1.1, 2 e 3
HTTP/1.1 e HTTP/2 normalmente usam TCP; HTTP/2 pode multiplexar requisições na conexão. HTTP/3 usa QUIC sobre UDP com TLS integrado. Não existe obrigatoriamente um TCP novo para cada fetch.
O que é um socket?
É uma interface de comunicação administrada pelo sistema operacional. Em TCP, o servidor mantém um socket de escuta e aceita conexões; cada conexão é identificada pelos endereços e portas de cliente e servidor. Um mesmo servidor atende muitos clientes na mesma porta.
O JavaScript desta página não abre TCP bruto nem escolhe a porta efêmera: fetch e XMLHttpRequest delegam isso ao navegador. NAT, proxies e balanceadores podem alterar ou intermediar o caminho. WebSocket é um protocolo e uma API de mensagens persistentes; não é sinônimo de socket TCP nem uma etapa obrigatória de toda requisição.

05 · EVOLUÇÃO DO CÓDIGO
Do submit ao AJAX e às Promises
1. Submit HTML
O navegador envia o formulário e navega para a resposta. O botão de comparação usa GET e abre o JSON em outra aba. Um formulário também pode usar POST; navegação não é exclusividade de GET.
<form action="/busca" method="get">
  <input name="name">
  <button>Enviar</button>
</form>
2. AJAX com XHR
JavaScript recebe a resposta por eventos e atualiza parte da página. AJAX é a técnica; apesar do X histórico de XML, também pode transportar JSON.
const xhr = new XMLHttpRequest();
xhr.open('GET', url);
xhr.onload = () => { /* verificar status */ };
xhr.onerror = () => { /* erro de rede */ };
xhr.send();
3. Fetch e Promise
Fetch devolve uma Promise. .then encadeia operações; .catch trata rejeições. HTTP 404/500 não rejeita fetch por si só: confira response.ok.
fetch(url)
  .then(response => {
    if (!response.ok) throw new Error(response.status);
    return response.json();
  })
  .then(mostrar)
  .catch(mostrarErro);
4. Async/await
É uma forma de trabalhar com Promises, não outro protocolo. Await suspende a função assíncrona até a resolução; não congela toda a página.
try {
  const response = await fetch(url);
  if (!response.ok) throw new Error(response.status);
  const data = await response.json();
  mostrar(data);
} catch (error) { mostrarErro(error); }
Escolha os três modos no laboratório para comparar chamadas reais equivalentes. O adaptador XHR usa callbacks/eventos internamente e os envolve em uma Promise para compartilhar o fluxo da interface.


Continue a investigação no DevTools
  1. Abra Network antes de buscar. Filtre por Fetch/XHR e escolha uma requisição.
  2. Veja URL, método, Query String, status, resposta e cabeçalhos.
  3. Compare os modos: a intenção HTTP é igual, embora a API JavaScript mude.
  4. Ative as colunas Protocol e Remote Address quando disponíveis e examine Timing.
  5. Teste Offline e Cancelar. Falha de rede/CORS pode impedir o acesso a qualquer status HTTP.
