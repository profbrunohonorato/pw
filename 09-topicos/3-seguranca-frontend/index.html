03 · SEGURANÇA

Entenda onde cada defesa funciona

XSS pode executar no navegador; CSRF envolve requisições autenticadas; SSRF e SQL Injection dependem do servidor. HTTP Request Smuggling envolve a interpretação de mensagens entre servidores e proxies.

XSS: texto ou marcação?

Compare o mesmo comentário como texto e como HTML em um quadro isolado. O quadro tem sandbox sem permissão para scripts e uma política que bloqueia recursos externos.

Saída segura com textContent

HTML interpretado em sandbox

O sandbox impede a execução de código nesta demonstração. Isso não torna seguro usar innerHTML com entrada não confiável no documento real. No README, veja XSS refletido, armazenado e baseado em DOM.

CSRF: simule a decisão do servidor

Modelo local, sem login ou requisição real. Um token válido é comparado a uma sessão fictícia; no sistema real, quem verifica é o back-end.

Este modelo exige origem confiável e token válido. SameSite é uma camada adicional; CORS e CAPTCHA não substituem a proteção contra CSRF.

Zombie Cookie: entenda a restauração

Grave uma preferência fictícia em cookie e localStorage. Depois apague só o cookie e clique explicitamente em Restaurar. A cópia permite que o valor reapareça. Nenhum identificador é criado e não há restauração automática.

Recriar identificadores contra a escolha de quem os apagou compromete sua privacidade. O exemplo existe para mostrar como reconhecer e remover todas as cópias.


Camadas de proteção
Navegador → CDN / WAF → aplicação → banco de dados
reCAPTCHA
Ajuda a avaliar automação. Exige configuração no provedor e verificação do token no servidor.
CDN
Distribui conteúdo e reduz latência. Não torna o código da aplicação seguro por si só.
WAF
Inspeciona tráfego HTTP com regras e pode bloquear requisições. Atua como defesa adicional.
Os tutoriais no README cobrem também SSRF, SQL Injection, MIME Sniffing e HTTP Request Smuggling. Eles exigem controles no servidor, no banco ou na infraestrutura.
